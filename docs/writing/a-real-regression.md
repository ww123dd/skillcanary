# 发布前，门禁替我们拦下了一份不该公开的文件

前几天我们准备把一个内部项目开源。

准备工作做完之后，仓库里的状态是这样的：169 个文件全部 staged，而 main 分支上**一个 commit 都还没有**——也就是说，这个项目从来没有真正"发布"过，所有东西都停在工作区里。

就在这一步，发布检查里的一条规则拦住了我们。

它叫 privacy scan，管的事情很简单：扫描私有路径、内部账号、以及不该出现在公开仓库里的材料。这条规则真正拦住的东西，和代码一点关系都没有——待提交的列表里，躺着两份**第三方文章的阅读笔记**。

放在本地没问题，那本来就是我的读书笔记。但一旦推成公开仓库，它就成了公开内容：既有版权上的含糊，也不是这个项目应该对外呈现的东西。而当时我正忙着看代码、看测试、看 README 写得好不好——我根本不会去看一个叫 docs/reading/ 的目录里有什么。

同一轮扫描还抓出另一处：benchmark 的一个测试夹具里写着 ‹盘符›:\Users\‹账号›\secret。它只是一个用于验证"敏感路径能不能被识别"的假字符串，功能上完全正确，但放在公开仓库里，就是一个真实的本地账号名。

两处都不是 bug。它们在功能上都没有错。它们错在**不该出现在那个位置**。

处理方式很克制：把 docs/reading/ 写进 .gitignore，从索引里移除（文件仍然留在本机），把那个路径换成通用写法，然后第一个 commit 才落地。

这件事上有两点值得说：

第一，**人眼一定会漏这一类的错**。因为它不在你正在看的那条线上——你在看逻辑、看测试覆盖、看文档措辞，而"这份东西该不该公开"是另一条完全不同的问题。

第二，门禁的价值不在于它比你聪明。它能做的事很笨：扫几类字符串。它的价值在于**它不会因为赶时间而跳过**。我会赶时间，它不会。

这也是我在做的那个东西的全部意义：不让"我记得要检查"成为唯一的安全保障。规则要靠被想到、被加载才生效；机制不靠，它每次都会跑。
